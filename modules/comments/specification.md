## 1. Module Overview

The `comments` module lets authenticated Users and Support Agents add free-text comments to a ticket and read the comment thread of a ticket. Comments are the only communication channel between the ticket owner and the handling agent. The module consists of two REST endpoints (`POST` and `GET /api/tickets/{id}/comments`), a `comments` table, and the comments section plus add-comment form on the **Ticket Details** screen.

## 2. Objective

- Allow the ticket owner (User) and Support Agents to exchange information on a ticket (REQ-040).
- Present the full conversation of a ticket, with author name, role and timestamp, on Ticket Details (REQ-041).
- Enforce the access rules (User: own tickets only; Agent: all tickets — A-05), block commenting on Closed tickets (A-06, Provisional), keep comments immutable (A-06) and render comment text safely (REQ-060).

## 3. Scope

**In scope**
- `POST /api/tickets/{id}/comments` — add a comment.
- `GET /api/tickets/{id}/comments` — list comments of a ticket.
- Comments section and add-comment form on the Ticket Details screen (empty state, author name / role / timestamp display).
- `comments` table and its constraints.
- Permission checks (role + ownership), Closed-ticket blocking, body validation (required, trimmed, max length), output encoding.

**Out of scope (cross-reference only)**
- Ticket creation and ticket field validation — module `ticket-management` (REQ-010..013).
- Status changes, assignment and ticket history — module `ticket-workflow` (REQ-030..038).
- Login, token issuance, session handling — module `authentication` (REQ-001..003).
- Dashboard counts and recent tickets — module `dashboard` (REQ-050..052).
- Comment edit / delete, comment attachments, notifications, internal (agent-only) notes: not requested by the client; excluded unless confirmed (`requirement.md` Section 18; OQ-02, OQ-23).

## 6. Business Rules

| ID | Rule | Source |
|---|---|---|
| CMT-BR-01 | A User can comment only on (and read comments of) their own tickets. | A-05, BR-10 |
| CMT-BR-02 | A Support Agent can comment on and read comments of all tickets. Restriction for agents on tickets assigned to a different agent: `TBD / Requires clarification` (OQ-17). | A-05 |
| CMT-BR-03 | No comment can be added to a `Closed` ticket. **Provisional** — client Rule 6 only says a closed ticket "cannot be edited". | A-06, BR-6, OQ-23 |
| CMT-BR-04 | Comments cannot be edited or deleted by anyone. | A-06 |
| CMT-BR-05 | Body is trimmed before validation and storage; a body that is empty after trimming is invalid. | A-15, OQ-22 |
| CMT-BR-06 | Body maximum length is 2000 characters (**Provisional**). | OQ-01 |
| CMT-BR-07 | Authorization (role, ownership) is evaluated before the Closed-ticket state check; a non-permitted caller always receives 403/404, never the state error. | REQ-002 (design decision, Provisional) |
| CMT-BR-08 | Commenting does not change the ticket status or the ticket history. | `requirement.md` Section 7 (history records status changes only) |
| CMT-BR-09 | Status of the ticket (Open, Assigned, In Progress, Resolved) does not otherwise restrict commenting by an authorised actor. | A-05, A-06 |

## 7. User Flow

**Flow A — User adds a comment (WF-1)**
1. User logs in, opens My Tickets and selects own ticket → Ticket Details.
2. The Comments section lists existing comments (or the empty state).
3. User types text in the add-comment form and submits.
4. Client-side validation passes → `POST /api/tickets/{id}/comments`.
5. API returns 201; the new comment appears at the end of the list with author name, role and timestamp; the form is cleared.

**Flow B — Agent replies (WF-2)**
1. Agent opens All Tickets → Ticket Details of any ticket.
2. Agent reads the thread and submits a comment as in Flow A.
3. The owner sees the comment on the next load of Ticket Details (no notifications — Section 18 of `requirement.md`).

**Flow C — Closed ticket**
1. Any actor opens a Closed ticket; existing comments are displayed (Provisional).
2. The add-comment form is replaced by an informational message; a direct API call returns 409 (Provisional).

**Flow D — Negative paths**: empty / whitespace-only / over-length body → inline error, nothing saved; another user's ticket → access denied; session expired → redirect to Login.

## 8. UI Requirements

Screen: **Ticket Details** (REQ-016, REQ-070). Layout/visual design: `TBD` (`requirement.md` Section 9). All texts below are **Provisional**.

| Element | Requirement |
|---|---|
| Comments section | Titled "Comments", positioned on Ticket Details below the ticket data. Lists all comments of the ticket, oldest first (Provisional). |
| Comment item | Shows author name, author role (User / Support Agent), timestamp in the viewer's local time zone (A-12; format TBD — OQ-20) and the body. Multi-line text keeps its line breaks. Long unbroken text wraps and does not break the layout. |
| Empty state | Text such as "No comments yet" when the ticket has no comments. |
| Add-comment form | Multi-line text area (label "Add a comment") and a submit button ("Add Comment"). Visible to a User on own non-Closed tickets and to an Agent on any non-Closed ticket. |
| Client-side validation | Empty or whitespace-only body → inline error "Comment is required"; body over 2000 characters → inline error "Comment must not exceed 2000 characters" (server stays authoritative). Whether the text area also hard-limits typing: `TBD`. |

| Closed ticket | Form hidden or disabled with message such as "This ticket is closed. New comments cannot be added." Existing comments remain visible (Provisional, OQ-23). |
| Edit / delete | No edit or delete controls on any comment (A-06). |
| Error handling | 401 → redirect to Login; 403/404 → "access denied / not found" page; 400 → inline error; 409 → banner with the server message; 500 → generic message. |
| Security | Comment text is inserted as text, never as HTML (REQ-060). |

## 9. API Requirements

Authentication: `Authorization: Bearer <token>` on every call (A-11). `{id}` = ticket internal id (A-09). Success status codes (201 / 200) are **Provisional** (OQ-26).

### 9.1 POST `/api/tickets/{id}/comments` — add comment

| Item | Value |
|---|---|
| Method / path | `POST /api/tickets/{id}/comments` |
| Request headers | `Authorization: Bearer <token>`, `Content-Type: application/json` |
| Request body | `{ "body": "string, required, 1-2000 chars after trim" }` |
| Ignored fields | Any other property (e.g. `userId`, `role`, `createdAt`, `ticketId`) is ignored; it never overrides server-derived values. |

Success response — `201 Created` (Provisional):

```json
{
  "id": 501,
  "ticketId": 1001,
  "author": { "id": 2, "name": "User One", "role": "USER" },
  "body": "Printer still shows error E-23 after restart.",
  "createdAt": "2026-10-07T09:15:30Z"
}
```

Error responses (contract from `requirement.md` Section 14; `error` codes are Provisional):

| HTTP | Condition | `error` | Example `message` |
|---|---|---|---|
| 400 (or 422 — OQ-26) | `body` missing, null, not a string, empty or whitespace-only after trim, longer than 2000 chars; malformed JSON; non-numeric `{id}` | `VALIDATION_ERROR` | "Validation failed" (details: `{ "field": "body", "message": "Comment is required" }`) |
| 401 | Missing, invalid or expired token | `UNAUTHORIZED` | "Authentication required" |
| 403 (or 404 — OQ-27) | User does not own the ticket | `FORBIDDEN` | "You are not allowed to comment on this ticket" |
| 404 | Ticket does not exist | `NOT_FOUND` | "Ticket not found" |
| 409 (or 400/422 — OQ-26) | Ticket status is `Closed` (Provisional, OQ-23) | `TICKET_CLOSED` | "Cannot add comments to a closed ticket" |
| 500 | Unexpected failure | `INTERNAL_ERROR` | Generic message; no stack trace or PII |

Error body shape example:

```json
{
  "status": 400,
  "error": "VALIDATION_ERROR",
  "message": "Validation failed",
  "details": [ { "field": "body", "message": "Comment must not exceed 2000 characters" } ]
}
```

### 9.2 GET `/api/tickets/{id}/comments` — list comments

| Item | Value |
|---|---|
| Method / path | `GET /api/tickets/{id}/comments` |
| Request headers | `Authorization: Bearer <token>` |
| Request body | None |
| Query parameters | None. Pagination / limit of comments: `TBD / Requires clarification` (OQ-34); until decided the endpoint returns all comments. |

Success response — `200 OK` (Provisional), oldest first:

```json
[
  {
    "id": 501,
    "ticketId": 1001,
    "author": { "id": 2, "name": "User One", "role": "USER" },
    "body": "Printer still shows error E-23 after restart.",
    "createdAt": "2026-10-07T09:15:30Z"
  },
  {
    "id": 502,
    "ticketId": 1001,
    "author": { "id": 3, "name": "Agent One", "role": "AGENT" },
    "body": "Please send a screenshot of the error.",
    "createdAt": "2026-10-07T09:20:05Z"
  }
]
```

A ticket without comments returns `200 OK` with `[]` (Provisional; envelope with paging metadata TBD — OQ-34).

| HTTP | Condition | `error` |
|---|---|---|
| 400 | Non-numeric `{id}` | `VALIDATION_ERROR` |
| 401 | Missing, invalid or expired token | `UNAUTHORIZED` |
| 403 (or 404 — OQ-27) | User does not own the ticket | `FORBIDDEN` |
| 404 | Ticket does not exist | `NOT_FOUND` |
| 500 | Unexpected failure | `INTERNAL_ERROR` |

### 9.3 Not provided (A-06)

`PUT` / `PATCH` / `DELETE /api/tickets/{id}/comments/{commentId}` do not exist; calling them returns 404 or 405 and never changes data.

## 10. Database Requirements

Table `comments` — columns are **Proposed** (`requirement.md` Section 11); the client specified no columns.

| Column | Type (proposed) | Constraints |
|---|---|---|
| `id` | BIGINT / INT | Primary key, auto-generated |
| `ticket_id` | BIGINT / INT | NOT NULL, FK → `tickets.id` |
| `user_id` | BIGINT / INT | NOT NULL, FK → `users.id` (author) |
| `body` | VARCHAR(2000) / TEXT | NOT NULL; stored trimmed; length ≤ 2000 (Provisional, OQ-01) |
| `created_at` | TIMESTAMP (UTC) | NOT NULL, default = server time (A-12) |

- No `updated_at` / `deleted_at` columns: comments are immutable (A-06).
- Recommended index: (`ticket_id`, `created_at`, `id`) for ordered listing.
- Behaviour on ticket deletion (cascade / restrict): `TBD / Requires clarification` (OQ-04).
- Writing a comment is a single insert; it does not touch `tickets` or `ticket_history` (CMT-BR-08). Whether `tickets.updated_at` changes on a new comment: `TBD` (OQ-38).

| # | Scenario | Layer | Expected behaviour |
|---|---|---|---|
| ES-01 | Empty or whitespace-only body | UI + API | Inline error (UI); 400 `VALIDATION_ERROR` (API); no row created |
| ES-02 | Body longer than 2000 characters | UI + API | Inline error (UI); 400 (API); no row created (Provisional limit) |
| ES-03 | `body` missing / null / wrong type | API | 400 `VALIDATION_ERROR` |
| ES-04 | Malformed JSON | API | 400; no stack trace |
| ES-05 | No / invalid / expired token | API + UI | 401; UI redirects to Login |
| ES-06 | User comments on or lists another user's ticket | API + UI | 403 (or 404 — OQ-27); no data disclosed |
| ES-07 | Ticket id does not exist | API + UI | 404 `NOT_FOUND` |
| ES-08 | Comment on a Closed ticket | API + UI | 409 `TICKET_CLOSED` (Provisional, OQ-23, OQ-26); UI form unavailable |
| ES-09 | Ticket becomes Closed while the form is open | UI + API | Submit returns 409; UI shows the message; text is kept |
| ES-10 | Non-numeric ticket id | API | 400 (or 404); no SQL error exposed |
| ES-11 | Database / server failure | API | 500 generic message; no row partially stored |
| ES-12 | Network failure on submit | UI | Error message; typed text retained; no duplicate created on retry unless the first request succeeded |
| ES-13 | Edit / delete attempt | API | 404 or 405; data unchanged |

## 13. Security / Permission Requirements

- Authentication on both endpoints (REQ-003); 401 otherwise.
- Server-side role **and** ownership check on every call; the UI check is never the only control (REQ-002, `requirement.md` Section 10).
- Ticket `{id}` tampering by a User must not reveal or create comments on another user's ticket (403/404 — OQ-27).
- Author identity is derived from the token only; client-supplied `userId`, `role`, `createdAt` are ignored (CMT-FR-03).
- Output encoding / sanitising of comment text to prevent stored XSS (REQ-060); `<script>`, event-handler attributes and HTML entities are displayed as literal text.
- Parameterised queries only; SQL metacharacters in body or path are treated as data (REQ-060, `requirement.md` Section 15).
- Error responses never contain stack traces, SQL text or other users' data.
- Comments are immutable; no endpoint exposes update/delete (A-06).
- Author data returned is limited to id, name and role (Provisional — OQ-36); password data is never returned (REQ-060).

## 16. Edge Cases

- Body exactly 1 and exactly 2000 characters (after trim); body of 2000 characters plus trailing spaces (accepted — trim first); 2001 characters (rejected). Limit is Provisional.
- Body containing only line breaks or tabs → treated as empty after trim.
- Body with Unicode, emoji (multi-code-unit characters), right-to-left text: length counting rule (characters vs UTF-16 units vs bytes) `TBD / Requires clarification` (OQ-01).
- Multi-line body: line breaks preserved on display; leading/trailing blank lines trimmed.
- Very long unbroken string (no spaces) must not break the page layout.
- Ticket with 100+ comments: all returned and shown in order; pagination behaviour TBD (OQ-34).
- Two comments created at the same second: order determined by `id` (Provisional).
- Rapid double-click on submit: one comment only (Provisional, OQ-37).
- Two users commenting at the same time: both saved, no loss, each with the correct author.
- Ticket closed by the owner while an agent has the form open: submit returns 409 and the typed text is kept.
- Comment text identical to an existing comment: allowed (no uniqueness rule).
- Ticket assigned to another agent: other agents can still comment (A-05) — restriction TBD (OQ-17).
- Deactivated author (`users.is_active = false`): display of historical comments unchanged — TBD (not covered by client).
- Ticket deleted (OQ-04): comment visibility and cascade TBD.
- Timestamp display across time zones and daylight-saving change: stored in UTC, shown in local time (A-12); format TBD (OQ-20).
