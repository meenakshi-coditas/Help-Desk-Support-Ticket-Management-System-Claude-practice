# Ticket Workflow — Test Cases

Test cases for the `ticket-workflow` module (prefix `WF`): assignment, status state machine, user close action, Update Ticket screen, Closed-ticket immutability, `ticket_history` recording/display and atomicity. They are derived from `modules/ticket-workflow/specification.md` and `requirement.md`. Expected results marked Provisional depend on assumptions (A-xx) or open questions (OQ-xx) listed in the Test Scenario cell; they must be re-baselined when the client answers. Ticket creation, comment blocking, login and dashboard counts are tested in their own modules.

## Common steps

| Code | Step |
|---|---|
| CS-1 | Authenticate: `POST /api/auth/login` with `{"email":"<account>","password":"<seed password>"}` (A-11); send the returned token as `Authorization: Bearer <token>` on every request. |
| CS-2 | Database check (read-only): `SELECT status, assigned_to, created_at, updated_at FROM tickets WHERE id=<id>` and `SELECT COUNT(*) FROM ticket_history WHERE ticket_id=<id>`. Record values before and after the action. |
| CS-3 | Reset fixtures to the table above before each case (or create a fresh ticket in the required state), so cases do not depend on each other. |

HTTP codes follow the provisional contract in requirement.md Section 14 (409 for invalid transition and Closed lock; 400 vs 422 per OQ-26).
