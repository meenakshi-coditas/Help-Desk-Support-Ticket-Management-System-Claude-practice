## 1. Project Architecture

A conventional three-tier web application, delivered as a **modular monolith** (one deployable backend, one SPA frontend, one database). The module split mirrors `modules/`; each backend module has its own routes, service, repository and validation, and talks to other modules only through their service interfaces.

```
 Browser (SPA)  ──HTTPS/JSON──▶  REST API (/api)  ──▶  Relational DB
  React UI                       Express app            PostgreSQL
                                 ├─ auth module         ├─ users
                                 ├─ ticket-management   ├─ tickets, categories, attachments
                                 ├─ ticket-workflow     ├─ ticket_history
                                 ├─ comments            ├─ comments
                                 └─ dashboard           └─ (aggregates on tickets)
                                 File storage (attachments)
```

Why a monolith: single small team/practice project, simple deployment, simple end-to-end testing; modules keep boundaries clean for later extraction if ever needed.

## 3. Frontend Architecture

- **Structure** (feature-based): `src/features/{auth,tickets,workflow,comments,dashboard}/` each with `api/`, `components/`, `pages/`, `hooks/`; shared `src/components`, `src/lib/http`, `src/routes`.
- **Routing**: `/login`, `/dashboard`, `/tickets` (My Tickets for User, All Tickets for Agent — same route, role-scoped data), `/tickets/new`, `/tickets/:id`, `/tickets/:id/update` (Agent). Route guards check authentication and role; unauthorised → redirect/403 page.
- **State**: server state via a query cache (TanStack Query); auth state in a small context; no global store beyond that.
- **HTTP layer**: one API client that attaches the token, normalises the error contract (requirement.md §14) and redirects to `/login` on 401.
- **Forms**: schema-validated, inline errors, submit-button disabled while pending (prevents double submit).
- **Testability (REQ-063)**: stable `data-testid` on every input, button, table row, status badge and message.

## 4. Backend Architecture

- Layers per module: `routes → controller → service → repository`. Controllers do HTTP only; services hold business rules; repositories hold SQL/ORM.
- Cross-cutting middleware: request id/logging, authentication, `requireRole`, ownership guard, validation, centralised error handler producing the single error contract, upload handling.
- **Workflow engine** (`ticket-workflow`): a single pure function/table `canTransition(from, to, actor, ticket)` is the only place that decides transitions (requirement.md §7); the same table drives UI button visibility through the API response (`allowedActions` on ticket details — proposed).
- **Transactions**: status change = update ticket + insert `ticket_history` in one DB transaction (REQ-062). Assignment uses a conditional update (`WHERE status='Open' AND assigned_to IS NULL`) to avoid double assignment under concurrency.
- Ticket number generated by a DB sequence (A-09), never by application code.

## 5. Database Architecture

- Tables per requirement.md §11: `users`, `tickets`, `categories`, `comments`, `ticket_history`, `attachments`.
- Enforcement in the database as well as the app: FK constraints, `NOT NULL`, `CHECK` on `priority`, `status`, `role`; `UNIQUE(ticket_number)`; `UNIQUE(users.email)`.
- Indexes: `tickets(user_id)`, `tickets(assigned_to)`, `tickets(status)`, `tickets(priority)`, `tickets(created_at)`, `comments(ticket_id, created_at)`, `ticket_history(ticket_id, changed_at)`.
- Migrations are versioned and repeatable; a **seed script** creates the accounts (A-08), categories (OQ-12) and optional demo/QA datasets (including the dashboard dataset defined in `modules/dashboard/test-case.md`).
- History is append-only: no UPDATE/DELETE path in code; optionally a DB trigger/permission to enforce.

## 6. API Architecture

- REST + JSON under `/api`, resource-oriented, plural nouns; endpoints per requirement.md §12 (client-listed + proposed additions, OQ-26).
- Auth: `Authorization: Bearer <token>`.
- Consistent success envelope (resource or `{ data, page, pageSize, total }` for lists) and the single error contract (requirement.md §14).
- List endpoint query contract (provisional, OQ-11): `page`, `pageSize`, `sort`, `order`, `search`, `status`, `priority`, `category`, `assignedTo`.
- API documented with an OpenAPI file generated/maintained alongside the code and used by API tests (contract checks).
- Idempotency/concurrency: state-changing endpoints return 409 on stale/invalid state.

## 7. Authentication / Authorization Approach

- **Authentication**: login (credentials per OQ-09) → verify hash → issue signed token (`sub`, `role`, expiry — expiry TBD OQ-09). Generic failure message; no user enumeration.
- **Authorization** is enforced server-side in three layers:
  1. *Authenticated?* (middleware) → 401.
  2. *Role allowed?* (`requireRole`) → 403 (e.g. User calling `/assign`).
  3. *Ownership / state rules?* (service) → 403/404 (User accessing another user's ticket; OQ-27) or 409 (invalid transition, closed ticket).
- UI hides disallowed actions, but is never the only protection.

## 9. Integration Strategy

- **Contract first**: agree OpenAPI definitions per module before UI work so backend and frontend can proceed in parallel.
- **Module boundaries**: workflow calls ticket-management's repository for ticket lookup; comments call workflow's `isClosed(ticket)`; dashboard reads through a read-only query service. No module writes another module's tables except workflow → `ticket_history`/`tickets.status`.
- **Environments**: local (Docker Compose) → CI (ephemeral DB) → staging.
- **Continuous integration**: every PR runs lint, type-check, unit, API/integration tests against a real database, then UI E2E smoke (P1 cases).
- Each module is merged only when its specification acceptance criteria are demonstrably met (traceability in `traceability.md`).

## 11. Error Handling Strategy

- One error contract (requirement.md §14) produced by a central error handler; domain errors are typed (`ValidationError`, `AuthError`, `ForbiddenError`, `NotFoundError`, `ConflictError`) and mapped to HTTP codes in one place.
- Validation returns **all** field errors at once.
- Unexpected errors: logged server-side with request id; client receives a generic message + request id.
- Frontend: field-level messages, toast/banner for server errors, global 401 handler, error boundary for rendering errors, explicit empty/loading/error states.
- Status codes for invalid transition / closed ticket (409 vs 400/422) are provisional (OQ-26).

## 12. Security Strategy

- Password hashing (argon2/bcrypt), minimum policy per OQ-09; secrets only via environment variables.
- Server-side authN/authZ on every route; ownership checks to prevent IDOR (`/tickets/{id}`); consistent 403/404 behaviour (OQ-27).
- Input validation + output encoding (React escapes by default; never `dangerouslySetInnerHTML` for user content); parameterised queries only.
- Attachments: allow-list of types, size limit, generated storage names, served as download with `Content-Disposition` and `X-Content-Type-Options: nosniff`, stored outside web root (rules per OQ-02).
- HTTP hardening: `helmet`, restricted CORS, rate limiting on login (OQ-09), HTTPS in non-local environments.
- Dependency audit in CI; no sensitive data in logs.
- Security test cases in each module's `test-case.md` are part of the release gate.

## 13. Deployment Considerations

- Containerised (Docker): `frontend` (static build served by a web server/CDN), `backend`, `postgres`; attachment volume or object store (OQ-02).
- Config via environment (`DATABASE_URL`, `JWT_SECRET`, `TOKEN_TTL`, `UPLOAD_DIR`, `CORS_ORIGIN`); no secrets in the repo.
- Pipeline: build → test → migrate → deploy; migrations run before the new backend version starts; rollback = previous image + backward-compatible migrations.
- Health endpoint (`/api/health`) and structured logs; backups for DB and attachment storage (retention OQ-25).
- Hosting/target platform: **TBD / Requires clarification**.
- Release checklist: migrations applied, seed accounts' passwords changed, all P1/P2 tests green, security checks green, open questions closed or accepted.

## 14. Risks and Mitigations

| # | Risk | Impact | Mitigation |
|---|---|---|---|
| R1 | Blocking open questions (OQ-02/03/04/05/06/08/09/13/17/23) unresolved | Rework of rules, tests and UI | Hold a clarification session before module 1 starts; unblocked work proceeds on documented assumptions (A-xx) |
| R2 | Assumptions (A-xx) later contradicted by the client | Spec/test churn | Assumptions centralised in `requirement.md`; tests tagged `[OQ-xx]` so impact is searchable |
| R3 | Transition rules spread across UI and API | Inconsistent behaviour, security gap | Single `canTransition` table server-side; UI driven by API `allowedActions` |
| R4 | Race conditions (two agents assign, concurrent status updates) | Double assignment, corrupt history | Conditional updates + transaction; concurrency tests (`WF`) |
| R5 | IDOR / privilege escalation | Data leak | Ownership guard in service layer; role/permission test sets per module |
| R6 | Attachment abuse (malware, huge files, path traversal) | Security incident, disk exhaustion | Allow-list, size limit, renamed storage, download-only serving |
| R7 | History incomplete if update and insert are not atomic | Audit gap (Rule 7) | Single transaction; rollback test (`WF` DB cases) |
| R8 | Dashboard counts diverge from list data | Loss of trust | Share the same filter definitions; cross-check tests against list endpoint (`DSH`) |
| R9 | Time zone / ordering ambiguity in history and recents | Flaky tests, wrong ordering | Store UTC, tie-break on id; OQ-20 |
| R10 | Technology stack not approved | Wasted setup | Approve stack (OQ-28) before Foundation tasks |
